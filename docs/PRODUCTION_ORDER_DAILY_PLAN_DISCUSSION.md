# 生产订单日计划与完成监督方案讨论稿

## 1. 背景

当前系统已经通过水洗唛扫码接口获取生产订单相关信息，并完成检验扫码、合格/不合格记录、查询分析等能力。

后续可能需要将系统向前延伸一层：每天先扫描水洗唛获取订单信息，再由用户填写当日计划生产数并下达给车间。检验员后续扫码检验时，系统根据当日订单计划监督现场完成情况。

本文档仅为意向方案讨论稿，不代表已批准实施变更。

## 2. 核心目标

- 建立“北京自然日 + 生产订单”的车间共享日计划。
- 检验扫码时校验订单是否属于今日已下达计划。
- 只控制合格完成数，不限制不合格记录。
- 查询分析中增加订单维度的当日完成情况。

## 3. 业务口径

### 3.1 计划范围

第一版按车间共享计划池处理，不拆分到具体产线。

原因：

- 现场产线之间可能临时调配人员、产能和订单。
- 如果计划拆到产线，发生调整时需要频繁释放、转移或重下达，维护成本较高。
- 车间共享计划更适合先实现监督目标，保留现场调度弹性。

### 3.2 日计划唯一性

同一北京自然日、同一生产订单，只允许存在一条有效计划。

建议唯一口径：

```text
planDate + productionOrderNo
```

### 3.3 今日计划数

今日计划数代表当天该订单允许完成的合格数量上限。

建议规则：

- 今日计划数必须大于 0。
- 今日计划数不能大于订单总数量。
- 今日计划数可以小于订单总数量，因为同一订单可能分多天生产。
- 管理员或计划人员可以调整今日计划数，调整动作需要进入操作记录。

## 4. 新增功能模块

### 4.1 生产计划下达

新增菜单建议命名：

```text
生产计划
```

或：

```text
订单计划
```

主要操作流程：

1. 用户扫描或输入水洗唛。
2. 系统调用现有生产订单接口。
3. 系统展示订单信息。
4. 用户填写今日计划生产数。
5. 用户保存并下达当日车间计划。

建议展示字段：

- 生产订单号
- 成品零件编号
- 成品产品名称
- 订单数量
- 今日计划数
- 已下达状态
- 创建人
- 创建时间
- 最近修改人
- 最近修改时间

## 5. 检验扫码控制规则

### 5.1 没有今日计划

如果扫码解析出的生产订单当天没有有效计划：

- 禁止录入合格。
- 禁止录入不合格。
- 提示：`该订单今日未下达生产计划`。

原因：没有下达计划代表今天不应接收该订单的检验记录。如现场确实临时生产，应先补下达今日计划。

### 5.2 有今日计划

如果订单存在今日有效计划：

- 允许录入不合格。
- 合格录入需要检查今日合格完成数。
- 合格完成数未达到今日计划数时，允许提交合格。
- 合格完成数达到今日计划数后，禁止继续提交合格。

提示建议：

```text
该订单今日计划已完成，不能继续录入合格品
```

### 5.3 不合格记录

不合格记录不占用今日计划数。

规则：

- 不合格不计入完成数。
- 不合格不减少剩余计划数。
- 即使合格完成数已经达到今日计划数，仍允许继续录入不合格。
- 查询分析中单独统计不合格数量和原因。

### 5.4 合格完成数

合格完成数只统计当前订单、当前北京自然日下的合格记录。

建议口径：

```text
same planDate
+ same productionOrderNo
+ result = QUALIFIED
```

如果当前系统已有“同一条码合格后不可重复录入”的规则，该规则继续保留。

## 6. 检验页面展示调整

在检验员扫码后，当前订单区域建议展示：

- 生产订单号
- 订单数量
- 今日计划数
- 今日合格完成数
- 今日剩余数
- 完成率

今日检验明细中仍保留产线字段，用于追溯实际由哪条产线完成。

建议文案：

```text
今日计划：500
已完成：320
剩余：180
```

## 7. 查询分析调整

统计看板新增“今日订单完成情况”。

建议字段：

- 生产订单号
- 零件号
- 产品名称
- 订单数量
- 今日计划数
- 合格完成数
- 不合格数
- 完成率
- 参与产线
- 状态

状态建议：

- 未开始：合格完成数 = 0，不合格数 = 0
- 进行中：合格完成数 > 0 且小于今日计划数
- 已完成：合格完成数达到今日计划数
- 有异常：存在不合格记录

状态可组合展示，例如“已完成 / 有异常”。

## 8. 数据模型建议

### 8.1 生产订单缓存

用于保存接口返回的订单信息，减少重复依赖接口，也便于追溯当时接口返回内容。

建议表：

```text
ProductionOrderCache
- id
- productionOrderNo
- partNumber
- productName
- orderQuantity
- rawJson
- fetchedAt
- updatedAt
```

### 8.2 日计划

建议表：

```text
DailyProductionPlan
- id
- planDate
- productionOrderNo
- partNumber
- productName
- orderQuantity
- plannedQuantity
- status
- createdBy
- createdAt
- updatedBy
- updatedAt
```

建议状态：

```text
ACTIVE
CLOSED
```

第一版可以只实现 `ACTIVE`，后续再扩展关闭计划。

### 8.3 检验记录关联

建议在检验记录中增加订单维度字段：

```text
productionOrderNo
dailyPlanId
```

其中 `dailyPlanId` 可用于精确关联当时计划，`productionOrderNo` 可用于查询和兼容分析。

## 9. 权限建议

建议第一版：

- 管理员：可以下达、修改、关闭计划。
- 查询用户：可以查看计划和完成情况。
- 检验员：不能维护计划，只在检验扫码时看到计划完成信息。

是否允许查询用户下达计划，需要后续根据现场角色职责再定。

## 10. 操作记录

正式实施时建议进入操作记录的动作：

- 新增今日计划。
- 修改今日计划数。
- 关闭今日计划。
- 扫码时因无今日计划被拦截。
- 扫码时因合格数达到计划被拦截。

其中拦截记录是否进入操作记录需要再评估。如果拦截频率较高，建议只记录业务操作，不记录每次拦截，避免操作记录噪音过大。

## 11. 待确认问题

后续正式进入 PCR 前，需要确认：

1. 生产订单号在接口返回中的准确字段名。
2. 订单数量字段是否稳定存在，单位是什么。
3. 同一水洗唛是否可能对应多个生产订单。
4. 今日计划是否允许跨天复制。
5. 今日计划是否允许关闭。
6. 查询用户是否可以下达计划，还是只能管理员下达。
7. 拦截记录是否需要进入操作记录。

## 12. 推荐第一版范围

建议第一版只做最小可用闭环：

- 新增订单计划菜单。
- 扫码查询订单并下达今日计划。
- 检验扫码按今日订单计划拦截。
- 合格完成数不能超过今日计划数。
- 不合格不占用计划数，计划完成后仍允许录入不合格。
- 今日检验页显示计划数、完成数、剩余数。
- 查询分析增加今日订单完成情况。

暂不做：

- 产线级计划分配。
- 多日计划排程。
- 自动从 ERP 拉取全部订单。
- 复杂计划审批流。
- 计划释放/转移流程。
