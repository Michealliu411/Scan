# 生产质量日报设计规格

**状态：** 已实施，待发布

## 1. 目标与边界

在“查询分析”中新增“质量日报”页签，按北京自然月和产线查询、展示并导出《生产质量日报表（一次下线合格率）》。该报表替代现场手工汇总，统计口径以同一产品标签的第一次检验为准。

本次覆盖：日报查询、动态不合格原因列、Excel 导出、更新后的生产订单接口字段映射和历史数据兼容迁移。

本次不覆盖：车间或工序基础数据、多车间/多工序报表、ERP/MES 回写、上游接口数据补全、班次统计。

## 2. 已确认业务规则

1. 查询范围按北京时间自然月；默认当前年月，可按年份、月份、产线筛选，产线默认全部。
2. 一条产品标签只取全生命周期最早的检验记录；该记录归属其首次检验所在的日期、月份、产线、车型和部件。
3. 后续返修、复检或最终合格不改变一次下线日报，也不会进入后续月份日报。
4. 人工将首次检验记录更正为不合格，或修改其原因后，日报立即采用更正后的当前值；变更历史继续通过既有操作日志追溯。
5. 报表行按 `日期 + 产线 + 车型 + 部件 + 工序` 汇总；生产车间和工序固定为“缝纫”。
6. 生产订单数量为该汇总行内不同生产订单的订单数量之和，同一订单的多个标签只累加一次；历史记录无生产订单缓存时按0计。
7. 生产数量为该汇总行内第一次检验标签的去重数量；合格品、不合格品由该首次检验记录的当前结果计数；合格率为合格品数量 / 生产数量。
8. 不合格原因列按缺陷代码升序展开当前启用的基础数据原因；数量为零的启用原因列仍展示，已停用原因不展示。一个首次不合格记录关联多个原因时，每个启用原因列均加一，因此原因列之和可大于不合格数量。
9. 接口字段 `成品车型` 显示为“车型”，`成品品名` 显示为“部件”；上游为空时保持为空，不由本系统替换或补值。
10. 仅 `QUERY`、`ADMIN` 角色可查询和导出；`INSPECTOR` 不可访问。

## 3. 方案比较与选择

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. 查询分析内独立页签 | 复用既有权限、产线筛选和 Excel 导出模式，新增“质量日报”页签与专用接口。 | 采用 |
| B. 在明细查询页增加导出按钮 | 无法承载固定报表表头、汇总行和动态原因列，易混淆明细与日报。 | 不采用 |
| C. 新增独立一级模块 | 视觉上可行，但会重复导航、权限和筛选实现，当前业务规模不需要。 | 不采用 |

## 4. 页面与交互

“查询分析”新增“质量日报”页签，布局已由业务确认：

- 筛选区：年份、月份、产线、“查询日报”和“导出 Excel”。
- 报表标题：`生产质量日报表（一次下线合格率）`。
- 报表元数据：年、月、生产车间“缝纫”、工序“缝纫”。
- 表头固定列：序号、月份、日期、产线、车型、部件、工序、生产订单数量、生产数量、合格品数量、不合格数量、合格率。
- 表头动态列：所有当前启用的缺陷原因，以两级表头归入“不合格统计 缺陷原因”。
- 页面表格允许横向滚动；导出文件保持同样的两级表头、列顺序和数据口径。

## 5. 接口与数据设计

### 5.1 外部生产订单接口

更新默认 `SCAN_LOOKUP_URL` 为：

`http://192.168.1.151/ZTPDA/ServerCommand/getProductionOrderByShuiXiMai`

请求方式保持 `POST`，请求体保持 `{ "Code": "水洗唛码" }`。返回仍以 `ErrCode === 200` 判断成功；业务失败不能提示为网络故障。

字段映射：

| 外部字段 | 系统字段 | 用途 |
| --- | --- | --- |
| 成品零件编号 | `partNumber` | 原有零件号 |
| 成品产品名称 | `productName` | 保留上游原始产品名称 |
| 成品车型 | `vehicleModel` | 报表“车型” |
| 成品品名 | `partName` | 报表“部件” |
| 生产订单编号 | `productionOrderNo` | 原有计划、扫码校验 |
| 生产订单数量 | `orderQuantity` | 原有计划下达 |

新字段允许为空，空值原样持久化。

### 5.2 数据迁移与历史兼容

`InspectionRecord.vehicleModel` 中的历史值实际来自旧接口的“成品产品名称”，不是车型。为避免历史报表错报：

1. 新增可空字段 `productName`、`partName`。
2. 迁移时将旧 `vehicleModel` 的值复制至 `productName`，再将旧 `vehicleModel` 清空。
3. 新扫码记录分别写入 `productName`、`vehicleModel`、`partName`。
4. 既有检验记录的数量、条码、结果、原因、时间、产线和审计记录不变；历史日报中车型和部件为空，直至未来有可追溯的上游数据补充，不进行猜测性回填。

### 5.3 日报查询接口

新增只读接口：

`GET /analytics/quality-daily-report?year=YYYY&month=MM&productionLineId=<optional>`

接口返回：查询年月、固定元数据、缺陷原因列定义和汇总行。汇总行携带以缺陷原因 ID 为键的数量映射，前端以接口返回的列定义渲染，Excel 使用同一数据集导出。

查询实现必须先按 `barcode` 全局选出最早检验记录，再筛选该最早记录是否在所选北京自然月和产线内；不得先按月份过滤后再取首次记录。

## 6. 权限、审计与异常

- 接口复用 `SessionGuard`、`RolesGuard`，仅允许 `QUERY`、`ADMIN`。
- 查询与本地 Excel 下载不写操作日志；检验结果、缺陷原因的更正继续使用既有审计日志。
- 参数不合法时返回明确业务错误；外部接口 `ErrCode !== 200` 返回“未查询到生产订单”等业务提示，网络/HTTP/响应结构异常按既有错误码区分。

## 7. 验收标准

1. 查询用户和管理员可进入质量日报，检验员无入口且调用接口被拒绝。
2. 同一条码多次检验时，只按最早记录进入首次检验月份的一个日报行。
3. 跨月复检不进入后续月份日报。
4. 人工更正首次检验结果或原因后，日报汇总与动态原因列同步变化。
5. 表格固定列、动态缺陷列、车间、工序和“部件”表头符合确认稿。
6. 导出 Excel 包含完整原因列、两级表头、所选年月和产线数据，并与页面总数一致。
7. 新接口字段正确持久化；旧数据迁移后不把旧产品名称显示为车型。
8. API、前端组件、迁移、导出、构建和浏览器关键流程验证通过。

## 8. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 缺陷原因较多导致页面过宽 | 页面横向滚动；导出完整展开，不裁剪列。 |
| 旧记录字段语义不正确 | 可逆的加字段迁移，保存旧值到 `productName`，不猜测车型/部件。 |
| 首次记录跨月误算 | 先全局确定首次记录、再按月份筛选，并用跨月测试覆盖。 |
| 上游接口字段为空 | 保持空值，不阻断扫码，不伪造数据。 |
